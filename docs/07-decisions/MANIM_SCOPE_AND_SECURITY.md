# Manim 动画能力边界与演进方向

> 状态：当前有效
> 更新日期：2026-08-22
> 适用范围：LearnMath 的模型生成 Manim 动画链路（API、Redis、Dispatcher、Renderer 和前端媒体卡片）

## 1. 当前结论

LearnMath 使用 Manim 生成数学教学动画。当前链路已经支持：

- 二维函数、参数曲线、向量、几何关系、导数、积分和概率示意；
- 复杂二维函数的数值近似，包括分形、级数和高频振荡图像；
- 处处连续但处处不可导的函数的有限项/有限采样近似，例如 Weierstrass 函数；
- 中文标题和说明文字，Renderer 镜像已内置 `fonts-noto-cjk`；
- Redis 排队、断网 Renderer 渲染、视频和海报回传。

当前不承诺完整支持：

- `ThreeDScene` 的真实三维相机、视角旋转和三维动画；
- OpenGL、GPU 依赖或需要显示服务器的渲染方式；
- 外部图片、音频、字体、网络资源和科学级仿真；
- 无限级数、无限分辨率或严格意义上的连续对象。此类内容只能生成有限时间、有限采样和有限项数的可视化近似。

## 2. 为什么当前限制为二维

这不是 Manim 的能力限制，而是对模型生成 Python 源码执行环境的主动约束。模型生成的源码会在 Renderer 容器中执行，因此第一阶段优先保证安全、可复现和可预测的资源消耗。

### 2.1 安全边界

Renderer 运行在无网络、只读文件系统、丢弃 Linux capabilities、禁止提权的容器中。源码静态策略还禁止文件读写、网络访问、启动进程、动态执行、外部媒体和外部 TeX 资源。三维本身不是安全漏洞，但三维 API、OpenGL 后端和外部资源会扩大执行面，增加策略遗漏和环境差异的概率。

### 2.2 资源和稳定性

当前默认资源上限为：

- 动画时长不超过 12 秒；
- 单个 Renderer 容器最多 1 个 CPU、768 MB 内存、128 个进程；
- 源码和输出文件有大小上限；
- Renderer 使用固定的 Cairo/软件渲染路径，不依赖 GPU 或显示服务器。

二维教学示意在这些上限下更容易稳定完成。三维曲面、相机运动、高网格分辨率和高频函数会显著增加内存、CPU、帧数和失败概率。

### 2.3 产品范围

当前 Manim 的产品定位是“帮助学生看懂动态关系的教学示意”，不是通用科学可视化平台。简单定义、计算题和纯文字证明默认不触发动画；只有动态变化、空间关系或分步过程能明显改善理解时，Agent 才应调用动画工具。

## 3. 当前实现约束

源码策略位于 `app/services/manim_policy.py`，模型提示和失败修复提示位于 `app/services/qa/prompt_builder.py` 与 `app/services/manim_repair.py`。当前约束包括：

```text
只能导入 manim、math、numpy
必须定义唯一的 GeneratedScene(Scene)
禁止文件、网络、进程、动态执行和外部资源
渲染时长最多 12 秒
只允许 low/medium 两种质量档位
```

因此，直接提交 `class GeneratedScene(ThreeDScene)` 会被策略拒绝，即使 Manim 本身可以渲染该场景。将 `ThreeDScene` 改成普通 `Scene` 只能画出静态二维投影，不能获得真正的三维相机行为。

## 4. 已验证的复杂图像边界

### 4.1 三维曲面

直接使用 Manim 可以渲染例如：

```python
z = sin(x) * cos(y)
```

但当前 LearnMath 用户链路不接受 `ThreeDScene`，因此这属于“底层引擎可行、产品策略暂未开放”。如果开放三维，必须增加专门的场景类型检查、相机初始化规则、网格分辨率限制和三维回归测试。

### 4.2 处处连续但处处不可导

可以绘制 Weierstrass 函数的有限项近似：

```text
W(x) = Σ (a^n) cos(b^n π x)
```

渲染结果是有限项、有限采样的图像，不应在 UI 或教学文案中表述为“计算机画出了无限对象本身”。应明确说明这是可视化近似，并在高频项过多时限制采样密度和渲染时间。

## 5. 可优化方向

以下是后续优化方向，不代表已经批准实施。

### P0：先保持当前二维链路稳定

- 为复杂二维函数增加采样点数、频率和曲线长度的预算估算；
- 在入队前检查预计对象数量、点数和动画时长，尽早给出可解释的失败原因；
- 为高频函数、分形和级数近似增加 golden cases，验证空白帧、锯齿、超时和输出过大；
- 把渲染器中的字体、TeX 和媒体依赖固定到镜像，保持离线包可复现；
- 继续记录队列等待时间、渲染时间、失败代码、输出大小和资源使用情况。

### P1：受控开放三维

不要简单删除 `GeneratedScene(Scene)` 检查。建议新增受控的三维模式：

1. 允许唯一的 `GeneratedScene(ThreeDScene)`，但只接受显式白名单中的三维对象和相机 API；
2. 固定 Cairo 软件渲染，暂不开放 OpenGL、外部纹理、视频纹理和音频；
3. 限制曲面 `resolution`、网格总面数、对象数量、相机运动次数和帧数；
4. 三维任务使用更低的默认质量或独立资源池，避免阻塞二维教学动画；
5. 增加三维场景的渲染超时、内存峰值和视觉非空检查；
6. 在 Prompt 中明确区分二维和三维请求，失败时说明“当前版本暂不支持三维”，不要生成看似三维但实际错误的二维替代物。

### P2：更强的可视化表达

- 支持分阶段动画：先显示定义，再显示变化，最后显示结论；
- 对复杂曲线显示采样说明、参数范围和近似警告；
- 为曲面、参数曲线和隐式曲线提供经过测试的模板，减少模型自由编写底层渲染代码；
- 允许后端选择“快速预览”和“高质量渲染”，但仍受统一资源上限约束；
- 将视频海报、中间帧和渲染日志纳入验收记录，便于定位模型代码问题与 Renderer 问题。

## 6. 放开三维前的验收条件

只有同时满足以下条件，才应把三维从实验能力提升为产品能力：

- 三维策略测试覆盖合法场景、越权调用、超分辨率和超时场景；
- 至少完成曲面、参数曲线、向量场和相机运动四类 golden cases；
- 在无 GPU 的干净 Docker 环境中稳定通过；
- 资源峰值、P95 渲染时间和失败率有明确基线；
- 三维任务不会绕过现有的网络隔离、只读文件系统和输出大小限制；
- 前端能区分排队、渲染、失败和“近似结果”，并向学生给出准确提示。

在这些条件完成前，二维范围不是临时 bug，而是当前版本的有意产品边界。
